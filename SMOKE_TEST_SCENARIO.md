# Сценарий smoke-тестирования Drill Cloud

## 1. Назначение

Документ предназначен для ручной проверки текущего состояния проекта перед передачей сборки, выкладкой на стенд или объединением крупных изменений.

Цель smoke-теста — быстро подтвердить, что пользователь может:

- войти в систему и выйти из неё;
- увидеть только доступные ему буровые;
- открыть буровую и перемещаться между её разделами;
- увидеть текущие показатели и live-график;
- построить и настроить архивные графики;
- посмотреть live-видео и корректные состояния отсутствия видео;
- изменить и сохранить пользовательские настройки;
- убедиться, что видеоархив выгружается на Яндекс.Диск.

Сценарий составлен по состоянию репозиториев `cloud` и `ui` в ветке `dev` на дату проведения проверки. Проверки Яндекс.Диска относятся к сервису `mqtt-ingest`.

## 2. Формат прохождения

Для каждого пункта поставить один из статусов:

- [ ] `PASS` — результат соответствует ожидаемому;
- [ ] `FAIL` — результат не соответствует ожидаемому, создан дефект;
- [ ] `BLOCKED` — проверка невозможна из-за окружения или отсутствия тестовых данных;
- [ ] `N/A` — проверка неприменима к данной сборке по согласованной причине.

Рекомендуемый формат комментария к проблеме:

```text
Статус: FAIL
Стенд и сборка: <URL, версия или commit SHA>
Шаг: <номер шага>
Фактический результат: <что произошло>
Ожидаемый результат: <что должно было произойти>
Вложения: <скриншот, видео, HAR, логи>
Дефект: <ссылка или номер>
```

## 3. Объём и приоритеты

| Приоритет | Что входит | Когда выполнять |
|---|---|---|
| P0 | Авторизация, список буровых, открытие буровой, показатели, архивный график, видео, выход | При каждой выкладке; ориентир 30–45 минут |
| P1 | Роли, отсутствие данных, несколько графиков, все способы zoom, настройки, Яндекс.Диск | Перед релизом; ориентир ещё 45–75 минут |
| P2 | Ошибки сервисов, переподключение, разные браузеры и размеры экрана | Для полного регрессионного smoke; по возможности |

Тест считается пройденным, если все применимые P0-проверки имеют статус `PASS`, нет блокирующих дефектов и согласован результат P1-проверок.

## 4. Предусловия и тестовые данные

### 4.1. Окружение

- [ ] Открывается URL тестируемого UI.
- [ ] `GET /api/health` возвращает успешный ответ.
- [ ] Доступны Keycloak, cloud API, PostgreSQL/TimescaleDB, MQTT/video relay.
- [ ] В браузере разрешены WebSocket, EventSource/SSE и Media Source Extensions.
- [ ] Зафиксированы URL стенда, дата, браузер, версия браузера и commit SHA сборок `ui`, `cloud`, `mqtt-ingest`.
- [ ] DevTools открыт на вкладках Console и Network; перед началом очищены старые ошибки и запросы.

### 4.2. Учётные записи

Подготовить:

1. пользователя с ролью `drill-admin` или `admin`, видящего все буровые;
2. пользователя с ролью вида `drill-edge-<edge-id>`, видящего одну или несколько назначенных буровых;
3. пользователя без ролей доступа к буровым;
4. при возможности — две разные учётные записи для проверки раздельного хранения настроек.

### 4.3. Буровые и данные

Подготовить или заранее определить:

| Обозначение | Требование |
|---|---|
| Буровая A | Есть текущие числовые показатели, новые SSE-события и история минимум за 24 часа |
| Буровая B | Нет текущих показателей либо есть период без исторических данных |
| Буровая C | Настроена минимум одна работающая камера |
| Буровая D | Камеры не настроены |
| Исторические данные | Желательно есть данные за 1 час, 6 часов, 24 часа, 7 и 30 дней |
| Показатели | Есть названия, технические теги, единицы измерения; желательно один `null` и один нечисловой/пустой результат |
| Видеоархив | Есть доступ к Яндекс.Диску и известны `YANDEX_DISK_REMOTE_ROOT` и camera ID |

Если один объект сочетает несколько условий, можно использовать одну буровую вместо нескольких.

## 5. Короткий обязательный прогон P0

Этот маршрут выполняется первым. Подробные варианты находятся в последующих разделах.

- [ ] Войти валидным пользователем.
- [ ] Убедиться, что открылся список доступных буровых.
- [ ] Найти буровую A поиском по имени или ID.
- [ ] Открыть буровую A и проверить сводку на странице «Обзор».
- [ ] Открыть «Показатели», увидеть значения и движущийся live-график.
- [ ] Открыть «Архив», выбрать показатель и увидеть архивный график за 24 часа.
- [ ] Изменить период на 1 час и приблизить график по X.
- [ ] Открыть «Видео», увидеть воспроизводящийся поток буровой C.
- [ ] Вернуться к списку буровых.
- [ ] Выйти из системы и убедиться, что защищённые страницы больше не доступны.

## 6. Подробные сценарии

### AUTH — вход, сессия, роли и выход

#### AUTH-01. Успешный вход — P0

1. [ ] Открыть UI в приватном окне браузера.
   - Ожидается: пользователь перенаправлен на страницу входа Keycloak; интерфейс буровых до авторизации не показан.
2. [ ] Ввести валидные логин и пароль, нажать вход.
   - Ожидается: открывается `/edges`, нет циклических редиректов и ошибок авторизации.
3. [ ] Обновить страницу браузера.
   - Ожидается: сессия сохраняется, повторный ввод пароля не требуется.
4. [ ] Открыть напрямую URL известной буровой `/edges/<edge-id>`.
   - Ожидается: страница открывается только при наличии доступа к этой буровой.

#### AUTH-02. Невалидный вход — P1

1. [ ] В приватном окне указать неверный пароль.
   - Ожидается: Keycloak показывает понятную ошибку; пользователь остаётся неавторизованным.
2. [ ] После ошибки войти с корректными данными.
   - Ожидается: вход успешен, предыдущая ошибка не мешает работе.

#### AUTH-03. Разграничение доступа — P1

1. [ ] Войти пользователем с ролью только для буровой A.
   - Ожидается: в списке есть A и нет неназначенных буровых.
2. [ ] Попробовать прямой URL неназначенной буровой.
   - Ожидается: данные буровой не раскрываются; API отвечает `403`, интерфейс показывает ошибку или безопасное пустое состояние.
3. [ ] Войти администратором.
   - Ожидается: доступны все заведённые буровые.
4. [ ] Войти пользователем без ролей буровых.
   - Ожидается: список пуст, данные чужих буровых недоступны.

#### AUTH-04. Выход — P0

1. [ ] Нажать «Выйти» на списке буровых или в верхней панели буровой.
   - Ожидается: сессия завершена, выполняется переход к Keycloak/экрану входа.
2. [ ] Нажать «Назад» в браузере и открыть сохранённый URL буровой.
   - Ожидается: защищённые данные не показываются из кэша, требуется повторная авторизация.

### EDGE — список буровых

#### EDGE-01. Загрузка списка — P0

1. [ ] Открыть `/edges`.
   - Ожидается: заголовок «Буровые установки», карточки без визуальных наложений и ошибок Console.
2. [ ] Сверить «Всего установок» с числом доступных пользователю карточек.
   - Ожидается: значения совпадают.
3. [ ] Проверить карточку буровой.
   - Ожидается: отображаются название и ID; кнопка «Подробнее» доступна.
4. [ ] Нажать кнопку обновления списка.
   - Ожидается: список обновляется без перезагрузки всей страницы, карточки не дублируются.

#### EDGE-02. Поиск — P0

1. [ ] Ввести часть названия буровой в разном регистре.
   - Ожидается: остаются совпадающие карточки, счётчик «Найдено» корректен.
2. [ ] Очистить поле и ввести часть технического ID.
   - Ожидается: поиск также работает по ID.
3. [ ] Ввести строку без совпадений.
   - Ожидается: карточек нет, показано корректное пустое состояние; ошибок нет.
4. [ ] Очистить поиск.
   - Ожидается: весь доступный список восстановлен.

#### EDGE-03. Открытие и возврат — P0

1. [ ] Нажать «Подробнее» на буровой A.
   - Ожидается: URL содержит корректно закодированный ID; открывается «Обзор» именно выбранной буровой.
2. [ ] Нажать «К списку» в верхней панели.
   - Ожидается: открывается `/edges`.
3. [ ] Повторно открыть буровую и нажать пункт «Буровые» в боковом меню.
   - Ожидается: результат тот же; переход не приводит к ошибке или полной потере сессии.

#### EDGE-04. Пустой список и ошибка API — P2

1. [ ] Проверить пользователя без доступных буровых.
   - Ожидается: понятное сообщение об отсутствии буровых, счётчики равны нулю.
2. [ ] На тестовом окружении временно сделать endpoint списка недоступным.
   - Ожидается: отображается «Не удалось загрузить список буровых…», интерфейс не падает.
3. [ ] Восстановить API и нажать обновление.
   - Ожидается: список появляется без повторного входа.

> Кнопки «Состояние байпасов», «Аварии приводов», «Техническое обслуживание» и периодичности на карточке сейчас не ведут на отдельные маршруты. В smoke достаточно убедиться, что они не ломают карточку; наличие бизнес-действия проверять только после отдельного включения функции в продуктовый маршрут.

### OVERVIEW — обзор буровой и навигация

#### OVERVIEW-01. Сводка — P0

1. [ ] Открыть буровую A.
   - Ожидается: ID буровой одинаков в URL, заголовке и данных страницы.
2. [ ] Проверить карточки «Всего показателей», `Live`, «Архив», «Последнее обновление».
   - Ожидается: числа не отрицательные; время имеет понятный формат; при отсутствии обновлений показан `-`.
3. [ ] Проверить индикатор источника в верхней панели.
   - Ожидается: при рабочем SSE показан статус live/SSE; интерфейс получает новые данные без ручного обновления.
4. [ ] Нажать ручное обновление.
   - Ожидается: сводка обновляется, нет дублей запросов или сброса страницы.

#### OVERVIEW-02. Навигация — P0

1. [ ] По очереди открыть карточки «Текущие показатели», «Архив и график», «Видео».
   - Ожидается: открывается соответствующий раздел той же буровой.
2. [ ] Повторить переходы через боковое меню: «Обзор», «Архив», «Показатели», «Видео».
   - Ожидается: активный пункт подсвечен, URL соответствует разделу.
3. [ ] Свернуть и развернуть боковое меню.
   - Ожидается: рабочая область корректно меняет ширину, кнопки остаются доступны, состояние сохраняется сервером.

### CURRENT — текущие показатели и live-график

#### CURRENT-01. Список показателей — P0

1. [ ] Открыть «Показатели» буровой A.
   - Ожидается: показаны виджеты с названием, техническим тегом, значением и единицей измерения, если она задана.
2. [ ] Сверить счётчик «Всего» с количеством видимых после текущего фильтра показателей.
   - Ожидается: счётчик соответствует списку.
3. [ ] Найти показатель по части названия.
   - Ожидается: видны только совпадения.
4. [ ] Повторить поиск по техническому тегу, группе или единице измерения.
   - Ожидается: поиск находит ожидаемый показатель.
5. [ ] Ввести строку без совпадений и затем очистить её.
   - Ожидается: пустой результат показан без ошибки; после очистки список восстановлен.
6. [ ] Проверить показатель со значением `null`.
   - Ожидается: интерфейс показывает безопасное пустое обозначение, а не `NaN`, `undefined` или падение страницы.

#### CURRENT-02. Live-обновление — P0

1. [ ] Выбрать показатель, который гарантированно меняется на источнике, и запомнить значение/время.
2. [ ] Не обновляя страницу, дождаться следующего события.
   - Ожидается: значение обновляется через SSE, «Последнее обновление» на обзоре меняется после возврата/обновления данных.
3. [ ] Открыть Network и проверить EventSource.
   - Ожидается: соединение длительное и без бесконечного частого переподключения.
4. [ ] Кратковременно прервать сеть и восстановить её.
   - Ожидается: приложение не падает; SSE переподключается либо включается fallback polling; после восстановления приходят свежие значения.
5. [ ] При недоступном SSE нажать ручное обновление.
   - Ожидается: актуальные значения можно получить через API.

#### CURRENT-03. Live-график — P0

1. [ ] Проверить блок «Живой график текущих значений».
   - Ожидается: для числовых показателей строятся линии, легенда соответствует названиям показателей.
2. [ ] Навести указатель на линию.
   - Ожидается: tooltip показывает время, название серии и отформатированное значение.
3. [ ] Подождать не менее двух интервалов обновления.
   - Ожидается: временное окно движется, новые точки добавляются без полной перерисовки страницы.
4. [ ] Проверить начальную загрузку истории.
   - Ожидается: виден индикатор загрузки, затем история и live-данные образуют непрерывный график без очевидных дублей.
5. [ ] Открыть буровую без числовых показателей.
   - Ожидается: сообщение «Нет числовых показателей для графика».
6. [ ] Остановить поток данных на время, не превышающее допустимый простой.
   - Ожидается: UI остаётся работоспособным, не генерирует неконтролируемое число запросов и ошибок.

#### CURRENT-04. Ошибка и отсутствие показателей — P1

1. [ ] Открыть буровую B без текущих данных.
   - Ожидается: пустое состояние, нулевые счётчики и отсутствие падения компонентов.
2. [ ] Временно сделать endpoint current недоступным.
   - Ожидается: показано «Не удалось загрузить текущие значения…».
3. [ ] Восстановить endpoint и нажать обновление.
   - Ожидается: данные появляются без повторной авторизации.

### HISTORY — архив и графики

#### HISTORY-01. Начальное состояние и выбор показателей — P0

1. [ ] Открыть «Архив» буровой A.
   - Ожидается: по умолчанию выбран период из настройки пользователя, в стандартной конфигурации — 24 часа; показана вычисленная грануляция.
2. [ ] Не выбирая показатель, проверить область графика.
   - Ожидается: подсказка предлагает раскрыть список и выбрать серию.
3. [ ] Раскрыть «Показатели».
   - Ожидается: видны доступные показатели и текущие значения; показано количество выбранных и найденных.
4. [ ] Найти показатель по отображаемому имени, затем по техническому тегу.
   - Ожидается: фильтр работает без учёта регистра.
5. [ ] Выбрать один показатель.
   - Ожидается: появляется chip, счётчик выбранных равен 1, график загружается.
6. [ ] Добавить ещё два показателя.
   - Ожидается: серии имеют различимые цвета; легенда и tooltip содержат выбранные показатели.
7. [ ] Удалить один показатель крестиком на chip и один — повторным нажатием в списке.
   - Ожидается: соответствующие серии исчезают, остальные сохраняются.
8. [ ] Проверить «Выбрать все», затем «Снять все».
   - Ожидается: действия применяются к видимому результату фильтра; после снятия всех возвращается placeholder.
9. [ ] При пустом поисковом запросе нажать `Backspace`, затем `Esc`.
   - Ожидается: `Backspace` удаляет последний выбранный chip, `Esc` закрывает список.

#### HISTORY-02. Данные, tooltip и отсутствие данных — P0

1. [ ] Выбрать показатель с известной историей.
   - Ожидается: график показывает агрегированные `min/avg/max`; нет лишней дублирующей линии.
2. [ ] Навести указатель на разные временные точки.
   - Ожидается: tooltip не выходит за экран, показывает корректное время и значения выбранных серий.
3. [ ] Выбрать период, в котором данных заведомо нет.
   - Ожидается: «Нет данных для выбранного диапазона», старые данные не выдаются за новые.
4. [ ] Вернуться к периоду с данными.
   - Ожидается: график снова строится без перезагрузки страницы.

#### HISTORY-03. Периоды — P0

1. [ ] Последовательно нажать пресеты «1 час», «6 часов», «24 часа», «7 дней», «30 дней».
   - Ожидается: поля «С» и «По», X-ось и грануляция меняются согласованно; активный пресет подсвечен.
2. [ ] Вручную изменить дату и время «С» и «По».
   - Ожидается: подсветка пресета снимается, загружается точный заданный диапазон.
3. [ ] Проверить диапазон на границе суток и месяца.
   - Ожидается: подписи оси корректны, нет сдвига на часовой пояс или на один день.
4. [ ] Проверить очень короткий и длинный допустимый диапазон.
   - Ожидается: UI остаётся отзывчивым, автоматически подбирается разумная грануляция.

#### HISTORY-04. Масштабирование по X и Y — P0

1. [ ] Навести указатель на график и прокрутить колесо без клавиш.
   - Ожидается: меняется масштаб только по времени X; данные для нового диапазона подгружаются, выбранные серии сохраняются.
2. [ ] Изменить диапазон нижними ручками X-слайдера и переместить выбранное окно.
   - Ожидается: график соответствует выделенному участку.
3. [ ] Удерживать `Shift` и прокрутить колесо.

### YDISK — видеоархив на Яндекс.Диске

> Это интеграционная smoke-проверка вне текущего UI: dev-интерфейс показывает live-видео, а `mqtt-ingest` записывает сегменты и выгружает завершённые файлы на Яндекс.Диск.

#### YDISK-01. Успешная запись и выгрузка — P1

1. [ ] Убедиться, что заданы `YANDEX_DISK_TOKEN`, `YANDEX_DISK_REMOTE_ROOT`, `ARCHIVE_BUCKET_SECONDS`, `ARCHIVE_UPLOAD_SCAN_SECONDS`.
   - Ожидается: в логах есть `uploader.started`, а не `uploader.disabled`.
2. [ ] Запустить или подтвердить поступление видео для известного camera ID.
   - Ожидается: в логах есть запуск ffmpeg и приём чанков; live-видео той же камеры работает в UI.
3. [ ] Дождаться завершения сегмента. На production defaults сегмент может занимать до 3600 секунд, скан выгрузки — до 300 секунд; для тестового стенда допустимо заранее установить короткие интервалы.
   - Ожидается: завершённый сегмент попадает в manifest и найден uploader-ом.
4. [ ] Проверить логи `upload.start` и `upload.done`.
   - Ожидается: удалённый путь имеет вид `<remote-root>/<camera-id>/YYYY-MM-DD/<file>`.
5. [ ] Открыть Яндекс.Диск и перейти в этот путь.
   - Ожидается: файл существует, размер больше нуля, дата и camera ID верны.
6. [ ] Скачать или воспроизвести файл.
   - Ожидается: запись открывается, содержит ожидаемую камеру и временной участок, длительность близка к длительности сегмента.
7. [ ] Проверить локальный каталог архива после `upload.done`.
   - Ожидается: успешно загруженный локальный файл удалён; другие незавершённые файлы не удалены.

#### YDISK-02. Отказ и повтор — P2

1. [ ] На тестовом окружении использовать недействительный токен или временно запретить сеть к API Яндекс.Диска.
   - Ожидается: есть `upload.error`; файл остаётся локально со статусом готовности к повтору и не теряется.
2. [ ] Восстановить доступ.
   - Ожидается: следующий scan повторяет выгрузку, появляется `upload.done`, файл затем удаляется локально.
3. [ ] Перезапустить `mqtt-ingest` при наличии готового локального сегмента.
   - Ожидается: сегмент находится по manifest и выгружается после запуска.
4. [ ] Проверить две камеры и переход на новую календарную дату.
   - Ожидается: файлы разложены по разным camera ID и папкам дат, не перезаписывают друг друга.

## 8. Функции, не входящие в обязательный smoke текущего маршрута

В кодовой базе есть компоненты электросхем и интеграции ТОиР light, но в текущем `AppRouter` ветки `dev` для них нет пользовательских маршрутов и пунктов меню. Поэтому их нельзя считать доступными функциями текущего UI.

После подключения к роутеру для них следует добавить отдельные проверки:

- опубликованная электросхема, переключение между схемами, live-теги по SSE, отсутствие опубликованных схем и ошибка diagram API;
- открытие ТОиР в iframe, корректный путь, тёмная тема, авторизация, навигация и недоступность внешнего сервиса;
- действия «Состояние байпасов», «Аварии приводов» и все периодичности технического обслуживания на карточке буровой.
